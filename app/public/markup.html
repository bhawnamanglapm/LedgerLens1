How the credit score is built

Six parts, each scored 0–100, weighted and added up to a score out of 1000.

{{b.band}} {{b.range}} → {{b.dec}}

Hard rules can override the band: tampering, structured cash deposits or circular money flows send the case for review, and EMIs above 65% of income decline it.

Built-in safeguards

  • 22 data validation checks, such as the running balance on every row, opening vs closing balance, duplicates and date gaps.
  • Page-order check stops the run if pages are jumbled or missing.
  • Smart review asks a person only about items that can change the decision.
  • Provisional decisions until every open item is resolved.
  • Full audit trail of every run and step in the Activity log.

Good to know

  • With Rules only, files are read in your browser and never uploaded. With the LLM on, page text goes through your backend to the model.
  • The AI step calls Claude when the app runs with its backend (npm start + an API key). On this hosted page there is no backend, so rules do the work and are labelled as such.
  • OCR on scans can misread digits. The balance checks catch this and send the case for review.
  • Practice samples use made-up data for a fictional applicant.

Accepted formats & transaction format

What the extractor can read, what it can't, and what a readable transaction row looks like.
FILES
ACCEPTED
  • Digital PDF with a text layer (you can select the text)
  • Password-protected PDF — you enter the password
  • Text or markdown export (.txt, .md)
  • CSV export (.csv) with a header row
  • Several files in one upload (e.g. savings + joint + card)
NOT ACCEPTED
  • Images (.png, .jpg, .webp) — read by OCR in the browser, a few seconds per page
  • Scanned PDFs with no text layer — each page rendered and read by OCR; mixed PDFs OCR only the scanned pages
  • Excel (.xlsx, .xls, .xlsm) — every sheet read as one page; dates converted to DD/MM/YYYY
  • Word, HTML or email statements
  • Handwritten, blurred, skewed or very low-resolution scans — OCR confidence drops; check the review queue
  • Non-English scans (OCR language pack is English only)
  • Files with pages out of order (stops with an error)
TRANSACTION ROWS
ACCEPTED
  • Table with | separators: Date | Value Date | Narration | Debit | Credit | Balance
  • CSV with the same columns; quoted fields and commas inside amounts are fine
  • Plain PDF text: Date [Value Date] Narration Amount Balance
  • Plain PDF text with separate Debit, Credit and Balance amounts
  • Column names: Date / Txn Date / Transaction Date · Value Date · Narration / Description / Particulars / Details · Debit / Withdrawal · Credit / Deposit · Balance
  • Narrations that wrap onto a second line (re-joined)
NOT ACCEPTED
  • Rows without a date at the start
  • A single signed Amount column (e.g. −500.00 / +500.00)
  • Statements without a running Balance column (debit/credit can't be checked)
  • Columns in another order with no header row (assumed order: Date, Value Date, Narration, Debit, Credit, Balance)
  • Summary or reward-points tables (not read as transactions)
DATES
ACCEPTED
  • DD/MM/YYYY · DD-MM-YYYY · DD.MM.YYYY
  • DD/MM/YY (read as 20YY)
  • DD-MMM-YYYY · DD MMM YYYY (e.g. 05-Jan-2025, 05 Jan 2025)
  • YYYY-MM-DD
NOT ACCEPTED
  • MM/DD/YYYY (US order — would be misread as day/month)
  • Month first in words (Jan 5, 2025)
  • Dates with no year (05 Jan)
AMOUNTS
ACCEPTED
  • Indian or international grouping: 1,42,500.00 · 142,500.00 · 142500.00
  • Prefixes ₹, INR, Rs.
  • Cr / Dr after the amount
  • Two decimals in plain PDF text (e.g. 500.00)
NOT ACCEPTED
  • Amounts in brackets for debits: (500.00)
  • Plain PDF text amounts with no decimals (500)
  • Comma as the decimal point (1.234,56)
HEADER & FOOTER
ACCEPTED
  • Account Number / A/C No / Card Number
  • Account Holder / Cardholder / Customer Name
  • Account Type · Currency or “Amounts in INR” · Opening Balance
  • Bank name on a line containing “BANK”, or “Bank Name: …”
  • Footer “Page X of Y” or “Page X / Y” for the order check
  • Pages with no header — details carried from earlier pages
NOT ACCEPTED
  • Account details only inside a logo or image
  • Pages with no page numbers (order check falls back and is noted)

The LLM reads and understands. Code checks, scores and decides.

An LLM (large language model) is used where judgement is needed to read messy text. Anything that must be exact, repeatable or explainable to a regulator stays in plain code.

Where the LLM fits in the pipeline

Two main uses (steps 3 and 5) and two optional ones. Scoring and decisions never use it.

How the integration works

Browser→ Small backend (holds the API key)→ LLM API

The API key must stay on the backend, never in the browser.

One call per 3-page batch (step 3)

  1. Instructions: extract every transaction, return only JSON in this format, the counterparty is mandatory ("UNIDENTIFIED" if none), don't invent rows.
  2. Context: account, bank, currency and closing balance from the previous batch, so details carry across pages.
  3. Input: the text of the 3 pages.
  4. Output: a list of transactions in a fixed format. The model's tool/function calling forces it to follow the format.

Classification calls (step 5)

Only the unclear rows, in one grouped call. The model must pick from the taxonomy's category list and give a confidence. Anything under 70% still goes to the Review queue.

Scale: a 100-page statement means about 34 extraction calls plus 1–2 classification calls, run several at a time.

Where it is integrated in this build

The LLM is wired into extraction (step 3) and classification (step 5). It runs when the app is started with its backend and an API key; switch AI step → LLM (Claude) on Ingest.
